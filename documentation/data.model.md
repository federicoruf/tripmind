# Data Model

## Overview

TripMind uses two persistent data stores with separate responsibilities:

- Neon PostgreSQL stores user-scoped relational metadata and travel memory.
- Chroma stores vector embeddings for public travel guides and encrypted chunks from private user documents.

The application does not persist generated itineraries, original uploaded files, or Auth0 user profiles. Auth0 is the identity provider; its subject claim is the user identifier used by the backend.

## Relational Model (Neon PostgreSQL)

### Identity

TripMind does not maintain a local users table. The user ID values below are Auth0 subject claims, obtained from a validated access token. The backend never accepts a user identifier from a request body, query parameter, or path as  
authorization evidence.

### user_documents

The user_documents table contains metadata for files uploaded to the private RAG workflow. It does not contain the original file, extracted text, embeddings, or encryption keys.

| Column | PostgreSQL type | Constraints / behaviour |
| --- | --- | --- |
| id | UUID | Primary key; defaults to gen_random_uuid() |
| user_id | TEXT | Required Auth0 subject; used for every user-scoped read, update, and delete |
| filename | TEXT | Required original filename |
| status | TEXT | Required; defaults to processing; allowed values are processing, ready, and error |
| chunk_count | INTEGER | Required; defaults to 0; updated after successful vector storage |
| created_at | TIMESTAMPTZ | Required; defaults to now() |
| expires_at | TIMESTAMPTZ | Required; the document is retained for 30 days |

Indexes defined by the versioned SQL script:

| Index | Columns | Purpose |
| --- | --- | --- |
| idx_user_documents_user_id | user_id | List and count a user's documents |
| idx_user_documents_expires_at | expires_at | Find documents for scheduled cleanup |

#### Lifecycle and Constraints

1. The service validates the filename extension and file size before writing. Supported formats are .pdf, .md, and .txt; the maximum size is 10 MB.
2. A row is inserted as processing, with expires_at set to 30 days after creation.
3. The insert enforces a maximum of five non-expired documents per user.
4. Text is extracted, split into at most 200 chunks, embedded, encrypted, and written to Chroma.
5. The row becomes ready and receives the stored chunk count. If processing fails after row creation, it becomes error.
6. User-facing list and count queries include only rows with expires_at greater than now().
7. User deletion and scheduled expiry cleanup delete Chroma chunks first, then the PostgreSQL row. This ordering prevents orphaned vectors if Chroma deletion fails.

The status check constraint guarantees only recognized status values. The application, rather than a database constraint, enforces non-negative chunk_count and the active-document quota.

### user_memory

user_memory stores the current summarized travel preference memory for a user. It is read and upserted by backend/src/memory.ts.

| Column | PostgreSQL type / behaviour | Notes |
| --- | --- | --- |
| user_id | Unique key used by ON CONFLICT | Auth0 subject; one row per user |
| resumen_texto | Text value | Current memory summary generated by the application |
| updated_at | Timestamp set to now() on insert and update | Last memory refresh |

The code requires user_id to be unique or primary-key constrained for the upsert to work. A versioned DDL script for this table is not currently present in the repository; this definition is an application runtime contract, not a repository-managed migration. Add and document a versioned migration before changing this structure.

## Vector Model (Chroma)

### Collection: tripmind_guides

tripmind_guides stores public travel-guide chunks created by the ingest process. It is shared across users.

| Element | Value / structure |
| --- | --- |
| Collection name | tripmind_guides |
| Distance space | Cosine (hnsw:space: cosine) |
| Chunk identifier | Filename followed by a hyphen and its chunk index |
| Document value | Plain extracted guide text |
| Embedding | Gemini embedding generated with RETRIEVAL_DOCUMENT |
| Metadata | source: source label from the ingested guide |
| Query embedding | Gemini embedding generated with RETRIEVAL_QUERY |

Public-guide chunks are created from files in backend/src/rag/docs/. Text is chunked into 1,600-character windows with a 200-character overlap. Retrieval uses a distance threshold and removes exact duplicate text after whitespace normalization.

### Collection: tripmind_user_docs

tripmind_user_docs stores private RAG chunks. It is a shared physical collection, but every read and deletion is scoped by user metadata.

| Element | Value / structure |
| --- | --- |
| Collection name | tripmind_user_docs |
| Distance space | Cosine (hnsw:space: cosine) |
| Chunk identifier | Document UUID followed by a hyphen and its chunk index |
| Document value | AES-256-GCM encrypted chunk text, encoded as base64 |
| Embedding | Gemini embedding generated with RETRIEVAL_DOCUMENT |
| Metadata | user_id, document_id, expires_at |
| expires_at metadata | Expiry timestamp in milliseconds since Unix epoch |

The encrypted text format contains a random 12-byte nonce, a 16-byte authentication tag, and ciphertext. The application derives a per-user encryption key from DOCS_MASTER_KEY and the Auth0 user ID through HKDF. A chunk encrypted for one user cannot be decrypted with another user's derived key.

Private retrieval filters Chroma by both user_id and unexpired expires_at before decrypting returned chunks. It then resolves filenames from user_documents using the same user scope. Chroma metadata is therefore an access-control boundary as  
well as a retrieval filter.

## Cross-Store Relationships

document_id is not enforced by a cross-database foreign key because Chroma and PostgreSQL are separate systems. The application preserves consistency through the upload, deletion, and expiry-cleanup workflows.

## Data Retention, Privacy, and Deletion

- Private document metadata and vector chunks expire after 30 days.
- The original uploaded file exists only in request memory while it is processed; it is not saved to local disk, PostgreSQL, or object storage.
- Private chunk text is encrypted before it is stored in Chroma. Embeddings and metadata are stored separately from the plaintext.
- The cleanup job finds expired PostgreSQL rows, deletes matching Chroma chunks using both user_id and document_id, then deletes the relational row.
- Retrieval also filters expired Chroma chunks. This is a second protection if the cleanup job has not run yet.
- Losing or rotating DOCS_MASTER_KEY without a data migration makes existing encrypted chunk text unreadable.

## Validation and Integrity Rules

| Rule | Enforced by |
| --- | --- |
| Authenticated ownership for user-scoped operations | Auth0 JWT plus user_id predicates and Chroma metadata filters |
| Allowed document extensions | Application validation |
| Maximum document size (10 MB) | Application validation and HTTP body limit |
| Maximum active documents per user (5) | Conditional PostgreSQL insert query |
| Maximum chunks per document (200) | Application service |
| Document status values | PostgreSQL check constraint |
| Document expiry | PostgreSQL timestamp and Chroma metadata filter |
| Private chunk confidentiality and integrity | AES-256-GCM with derived per-user keys |
| Chroma/PostgreSQL deletion order | Application cleanup and delete workflows |

## Change Management

When changing this model:

1. Add an ordered, versioned SQL script for every PostgreSQL schema change.
2. Update this document, documentation/api-spec.yml, and the relevant backend standards in the same change when behaviour or public representation changes.
3. Preserve compatibility with existing encrypted chunks and collection metadata, or plan an explicit migration.
4. Validate ownership and expiry filters for every new private-data query.
5. Test successful processing, partial failures, deletion, expiry cleanup, and cross-user isolation before deployment.
